# 住宅マーケティング数値ダッシュボード — spec.md

住宅会社のマーケティング担当者と、担当代理店が共同で使う数値管理・レポートツール。施策（広告・オーガニック運用）から来場・契約までのファネル全体を一気通貫で入力・可視化し、月次目標に対する予実を管理する。

---

## 0. このドキュメントについて

これは Claude Code で実装するための仕様書（v1）。**「⚠️ 要相談」** が付いた箇所は、実装着手前に人間が決める。それ以外は本書の記述を正とする。

## 1. プロダクト概要

### コンセプト

住宅会社（クライアント）1社ごとに、施策（広告出稿・SNS運用等）〜反響〜来場〜見積もり／図面出し〜契約までのマーケティングファネルの数値を管理するダッシュボード。数値は住宅会社側と代理店側で入力を分担する（広告・運用系は代理店、来場〜契約系は住宅会社）。代理店は1社で複数の住宅会社クライアントを担当し、アカウントを切り替えながら横断的に確認する。

### 提供価値

- **住宅会社**: 施策の効果や来場・契約の状況を代理店と同じ画面で共有でき、月次目標に対する進捗を随時確認できる。
- **代理店**: 担当する複数クライアントの状況を1つのツールで管理・報告でき、クライアント提出用のレポート作成の手間を削減できる。
- **双方**: 月次目標（予実）に対する実績が常に可視化され、ファネルのどこがボトルネックかを共通認識にできる。

### 最重要要件

**施策（広告／オーガニック運用）→反響→来場予約→来場→見積もり／図面出し→契約という一連のファネルを、住宅会社・代理店が分担入力しながら1つのダッシュボードに統合して見られること**。入力の分担と閲覧の統合が両立することが品質の核。

## 2. ユーザーとロール

| ロール | 説明 | 認証 |
| :---- | :---- | :---- |
| 代理店担当者 (Agency Staff) | 契約代理店の社内スタッフ。担当する複数の住宅会社（クライアント）を切り替えて閲覧し、施策データの入力・目標設定を行う | 必要（自社 Google Workspace ドメインでの Google 認証、ドメイン一致時に初回ログインで自動発行、§4.1決定） |
| 住宅会社担当者 (Client Staff) | 住宅会社のマーケティング担当。自社の来場・見積もり・図面出し・契約データを入力し、ダッシュボード・レポートを閲覧する | 必要（メール + パスワードのアカウント発行制。代理店が登録したメールアドレスへの招待リンクからパスワードを設定） |

- v1 では代理店は1社のみを想定する（複数代理店が使う汎用 SaaS 化はしない）。
- 代理店・住宅会社、いずれの側も1社内に複数ユーザーを登録できるが、**同じロール内での権限差（閲覧専用／編集可 等）は設けない**。
- 代理店担当者は、自分が割り当てられたクライアントのみ切り替えてアクセスできる。

## 3. 用語定義

- **クライアント (Client)**: 代理店が担当する住宅会社。データはクライアントごとに完全に分離される。
- **拠点 (Location)**: クライアントに紐づく展示場・支店などの単位。代理店・住宅会社どちらからも登録・編集できる。データ入力時は「特定の拠点」または「全社共通（拠点未指定）」を選択できる。**会社全体の実績は、特定拠点に紐づくデータと全社共通（拠点未指定）データをすべて合算した値**とする（例: 拠点A + 拠点B + 全社共通 = 会社全体）。
- **施策 (Campaign)**: 反響を生む活動の単位。「広告（有料）」または「運用（オーガニック）」のいずれかの種別を持つ（§4.2 の施策マスタ参照）。取得方法として「手動入力」と「API連携」の2種類がある。
- **反響 (Lead)**: 施策経由の問い合わせ・資料請求。
- **広告アカウント接続 (Ad Account Connection)**: Google広告・Yahoo広告・Meta広告について、クライアントの広告アカウントを OAuth 認証でこのツールに接続すること。代理店・住宅会社のどちらの管理画面からも接続できる（§4.2.2）。
- **ファネル (Funnel)**: 施策 → 反響 → 来場予約 → 来場 → 見積もり／図面出し → 契約、という一連の流れ。
- **見積もり (Estimate) / 図面出し (Floor Plan Proposal)**: 商談段階を構成する2つの通過点。案件により片方のみ、または両方を通過する。`funnel_metrics` は案件単位の紐付けを持たず期間集計件数のみを扱うため、**「いずれか一方でも通過した数」は自動算出しない（決定済み・v1では非対応）**。ダッシュボードでは見積もり数・図面出し数をそれぞれ個別の指標として表示する。
- **期間種別 (Period Type)**: データ入力・集計の単位。「月次」「週次」を入力ごとに選べる。
- **目標 (Target)**: 代理店がクライアントごと・KPIごとに設定する月次目標値。
- **予実 (Target vs Actual)**: 目標と実績の対比。
- **レポート (Report)**: 指定期間について、ファネル・チャネル別・拠点別・予実をまとめた集計ビュー。画面閲覧・PDF出力の両方に対応する。

## 4. 主要機能

### 4.1 アカウント・クライアント・拠点管理

- 代理店担当者が新規クライアント（住宅会社）を登録し、その際に住宅会社側の初期ユーザーアカウントを発行する。
- 拠点（展示場・支店等）は、代理店側・住宅会社側どちらからも登録・編集できる。導入初期は代理店側がまとめて登録することを想定する。
- 追加のユーザー招待は、代理店・住宅会社いずれの管理画面からも、自分の所属側のユーザーを追加できる。
- **外部連携ID（2026-08-27新規）**：今後さまざまな外部アプリ・システムと連携する際にこのクライアントを識別できるよう、内部PK（`clients.id`、UUID）とは別に、代理店が任意の値を自由に入力・編集できる識別子（`clients.external_client_id`）を持つ。クライアント登録画面で入力でき、登録後もクライアント一覧画面からいつでも変更できる。未設定のままでもよい（任意項目）。他クライアントと重複する値は設定できない。

#### 4.1.1 認証方式（2026-08-20 決定）

代理店・住宅会社で認証方式が異なる（決定済み）。

- **代理店担当者（Google 認証・招待不要）**：代理店社内の Google Workspace ドメイン（環境変数 `AGENCY_GOOGLE_WORKSPACE_DOMAIN` で管理）に属する Google アカウントであれば、`/login` の「Googleでログイン」から初回ログイン時に `agency_users` 行が自動発行される。ドメインが一致しない Google アカウントでのログインは拒否する（サインイン自体は成立しても、コールバック処理でドメイン不一致を検知し即座にサインアウトさせる）。個別の招待作業は不要（ドメイン所属自体が信頼の担保）。Google OAuth クライアント（Google Cloud Console での Client ID/Secret 発行・Supabase Dashboard への設定）は実装と別に外部作業として必要（§10 のフェーズドロールアウト対象 D1 と同種の外部依存）。
- **住宅会社担当者（メール招待・パスワード発行制、既存方針のまま）**：住宅会社は社ごとにメールドメインが異なり組織的な認証基盤を持たないため、代理店担当者がメールアドレスを登録すると招待メールが送信され、本人がリンクからパスワードを設定してログインする。Google ログインの選択肢は設けない（v1では）。
- ログイン画面（`/login`）は、上記2方式を1画面内に共存させる（§12 DESIGN_SYSTEM.md §5.9のパターンを踏襲しつつ、Googleボタンとメール+パスワードフォームを併記）。

### 4.2 施策データ入力・連携

施策には「広告（有料）」「運用（オーガニック）」の2種別があり、さらに取得方法として「手動入力」と「API連携」の2種類がある。

**入力項目（種別ごと）**

| 種別 | 入力項目 |
| :---- | :---- |
| 広告 | 施策費用、表示回数、クリック数、反響数（問い合わせ・資料請求） |
| 運用（オーガニック） | フォロワー数、投稿数、再生数、自社サイトへの流入率、反響数（問い合わせ・資料請求） |

**算出項目（広告のみ、決定済み）**

上記の入力項目に加えて、以下の指標をチャネル別内訳・レポート（§4.5, §4.6）に表示する。これらは入力・保存はせず、表示のたびに算出する。

| 指標 | 算出式 |
| :---- | :---- |
| クリック率 (CTR) | クリック数 ÷ 表示回数 |
| クリック単価 (CPC) | 施策費用 ÷ クリック数 |
| 反響あたりの費用 (CPL) | 施策費用 ÷ 反響数 |

分母が 0（または対象データなし）の場合は算出不可として「-」表示する。期間・拠点を集計した後の合計値に対して算出する（日別・行別に算出した値を平均するのではない）。

**表示回数・クリック数の入力を任意とする施策（決定済み）**

初期施策マスタのうち **TVCM・ポータルサイト（SUUMO/HOME'S等）・チラシ・折込** の3施策は、表示回数・クリック数の性質上、必須入力としない（任意項目とする）。これらの施策は施策費用・反響数のみを入力すれば、反響あたりの費用（CPL）を算出・表示できる。表示回数・クリック数が未入力の場合、クリック率（CTR）・クリック単価（CPC）は算出不可として「-」表示する。上記以外の広告施策（Google広告・Yahoo広告・Meta広告・YouTube広告・TikTok広告・Pinterest広告）は、引き続き表示回数・クリック数も入力項目とする。

**初期施策マスタ（v1 確定・追加可）**

| 施策 | 種別 | 取得方法 |
| :---- | :---- | :---- |
| Google広告 | 広告 | API連携 |
| Yahoo広告 | 広告 | API連携 |
| Meta広告（Facebook/Instagram） | 広告 | API連携 |
| YouTube広告 | 広告 | 手動 |
| TikTok広告 | 広告 | 手動 |
| Pinterest広告 | 広告 | 手動 |
| TVCM | 広告 | 手動 |
| ポータルサイト（SUUMO/HOME'S等） | 広告 | 手動 |
| チラシ・折込 | 広告 | 手動 |
| SEO／オーガニック検索 | 運用（オーガニック） | 手動 |
| Instagram運用 | 運用（オーガニック） | 手動 |
| YouTube運用 | 運用（オーガニック） | 手動 |
| TikTok運用 | 運用（オーガニック） | 手動 |
| Pinterest運用 | 運用（オーガニック） | 手動 |
| 自社HP | 運用（オーガニック） | 手動 |
| 住宅展示場 | 運用（オーガニック） | 手動 |

#### 4.2.1 手動入力（代理店）

- 上記マスタのうち「手動」の施策について、代理店担当者が期間（月次 or 週次を選択）・拠点（特定拠点 or 全社共通）を指定して数値を入力する。

#### 4.2.2 広告API連携（Google広告・Yahoo広告・Meta広告、v1 確定）

- クライアントごとに、Google広告・Yahoo広告・Meta広告の広告アカウントを OAuth 認証で接続する。接続操作は代理店・住宅会社どちらの管理画面からも行える。
- 接続後は日次で自動的に費用・表示回数・クリック数・反響数を同期する。反響数は各媒体側のコンバージョン計測（問い合わせ・資料請求フォームへのコンバージョンタグ設定を前提）から取得する。
- **反響数としてカウントするコンバージョンアクションは、広告アカウントごとに担当者が選択する（決定済み）**。OAuth 接続後、システムは当該アカウントに設定されているコンバージョンアクション一覧を媒体 API から取得して選択肢として提示する。担当者はそのうち「反響（問い合わせ・資料請求等）」に該当するものを複数選択でき、選択されたアクションの合算値を同期のたびに「反響数」として記録する。初期状態（未選択時）は取得できた全コンバージョンアクションを選択済みとして扱い、担当者が必要に応じて対象を絞り込む。選択は接続後いつでも変更でき、変更以降の同期分（および変更後に実行した「今すぐ同期」）から新しい選択が反映される。
- 自動同期に加えて、担当者が任意のタイミングで「今すぐ同期」を実行できる。
- 同期されたデータも、他の手動入力チャネルと同様に手動で上書き修正できる（連携エラーや数値のズレを補正するため）。**一度手動で上書きした期間・施策の行は、以降の自動同期で自動的に上書きされない**（担当者が明示的に「APIの値に戻す」操作をした場合のみ、再度 API の値で上書きされる）。
- 広告アカウントの接続状態（正常・エラー・未接続）は施策データ入力画面に表示し、認証切れ等のエラー時に担当者が気づけるようにする。
- 前提条件（⚠️要相談）: Google Ads API・Yahoo!広告 API・Meta Marketing API はそれぞれ開発者アカウント登録やアプリ審査が必要な場合がある。実装着手前に各媒体の申請要否・所要期間を確認する。

**フェーズドロールアウト（決定済み）**

各媒体の API 審査（§10）が完了する前でも開発・運用を止めないため、以下の方針で進める。

- **実装は v1 に含める**。OAuth 接続・自動同期・コンバージョンアクション選択（§4.2.2 上記）のコードは、審査結果を待たずにテスト用アカウント（Google の Test Account Access 等）で開発・検証を進める。
- **本番での有効化は媒体ごとに審査完了後**とする。媒体単位の審査状況を `platform_integrations`（§6）で管理し、審査待ちの媒体は、代理店・住宅会社どちらの接続画面でも OAuth 接続ボタンを非活性にし、「審査待ち」ステータスを明示する（`ad_connections` の 'connected' / 'error' / 'disconnected' とは別に、媒体単位の状態として表示する）。
- **審査待ちの媒体は、その間 §4.2.1 の手動入力と同じ入力フォームで運用する**（施策マスタ上の取得方法は変わらないが、実運用上は手動チャネルとして扱う）。審査待ち期間中に手動入力された行は `manually_overridden = true` として記録し、審査完了後に自動同期を有効化しても、既存の手動入力データが同期処理で上書きされないようにする。
- 審査状況（`platform_integrations.status`）の切り替えは、開発運用側が各媒体の承認を確認したうえで行う。専用の管理画面は設けず、v1 では運用側の直接更新で対応する。
- クライアントごとの OAuth 接続自体（担当者が実際に接続操作を完了するタイミング）が、媒体の審査完了後も遅れるケースがある。この場合も、当該クライアントの当該チャネルは接続完了まで手動入力で運用を継続する（`ad_connections` が存在しない、または `status = 'disconnected'` の間は常に手動入力可能というのは既存仕様のまま変更なし）。

#### 4.2.3 施策マスタのクライアント別管理（2026-08-10確認）

- §4.2 の初期施策マスタ17件は全クライアント共通のデフォルトとする。加えて、**クライアントごとに固有の施策（媒体）を追加できる**（例: 地元フリーペーパー等、初期マスタに無い特殊な媒体）。
- クライアント固有の施策は**代理店担当者のみが追加・編集できる**（住宅会社側には追加権限を持たせない）。追加・編集は `/agency/clients/[id]/campaigns` の施策マスタ管理画面で行う。
- クライアント固有の施策は取得方法「手動」のみとする（API連携は§4.2.2の3媒体に限定するため、追加施策をAPI連携対象にはしない）。
- 施策ごとに、**入力項目（施策費用・表示回数・クリック数・フォロワー数・投稿数・再生数・自社サイトへの流入率）のうちどれを使うかをチェックボックスで選択**し、選択した項目のみ入力フォームに表示する。反響数は全施策共通で常に入力必須のため、この選択の対象外とする。入力項目に「施策費用」を含む場合、費用は必須項目とする（他の選択項目は任意）。
- 初期施策マスタ17件の入力項目（表示回数・クリック数が任意のTVCM・ポータル・チラシ折込を含む）は、この仕組みの初期値として個別に設定済みとし、代理店側からの編集はできない（誤操作でデフォルトの挙動が変わることを防ぐため）。

#### 4.2.4 制作・クリエイティブ費用（2026-08-10確認）

- 施策（反響を生む媒体・活動）とは別に、**バナー制作・ページ更新など制作・クリエイティブ業務にかかった費用**を項目単位で入力できる（例: 「見学会バナー制作 40,000円」「ページ更新 15,000円」）。
- 項目名（自由入力のテキスト）・金額・期間（月次/週次）・拠点（特定拠点/全社共通）を入力する。あらかじめ項目を登録するマスタは設けず、都度自由に項目名を入力する。
- 施策の反響数・CTR/CPC/CPL等の算出には影響しない（あくまで別枠のコスト集計）。ダッシュボード・レポートには、対象期間の**合計金額**を表示する（項目単位の内訳表示は入力画面のみで行う）。
- 入力は代理店担当者が `/agency/clients/[id]/campaigns` から行う。

### 4.3 来場・契約データ入力（住宅会社）

- 拠点（または全社共通）ごとに、期間（月次 or 週次を選択）で以下を入力する。
  - 来場予約数
  - 来場数
  - 見積もり数
  - 図面出し数
  - 契約（成約）数
- 契約金額（売上）は v1 では扱わない（決定済み）。契約の「件数」までを管理する。

### 4.4 目標設定（予実管理）

- 代理店担当者が、クライアントごとに月次で KPI 目標値を設定する。
- ダッシュボード・レポートで、目標と実績を常に対比表示する。
- **年間一括入力（2026-08-27確認）**: 目標・予算は「KPI（またはチャネル）×12ヶ月」のグリッドで年間分を1画面にまとめて入力・編集できる。グリッドの起点月はクライアントごとに設定する事業年度の開始月（`clients.fiscal_year_start_month`、デフォルト4月）に従う。
- **KPIの管理単位（2026-08-27確認・変更）**: 来場予約数・来場数・契約数は引き続き会社全体のみの目標値として`targets`に保存する（`funnel_metrics`にチャネルの紐付けが無いため）。**反響数の目標は会社全体の単一値としては持たず、チャネル別（§4.2.3の追加施策を含む）に設定する**（下記）。会社全体の合計反響数は、チャネル別目標を拠点別＋全社共通で自動合算した値として表示のたびに算出する（保存はしない）。
- **チャネル別の反響数目標・予算（2026-08-27確認・新規）**: 代理店担当者が、費用(cost)を持つ「広告」施策について、クライアントごと・拠点(または全社共通)ごと・チャネルごとに、月次で「反響数目標」「予算」を設定できる（`campaign_targets`、§6）。この2つの値から、想定単価（想定CPL = 予算 ÷ 反響数目標）を表示のたびに算出する（保存はしない。分母が0または未入力の場合は算出不可として「-」表示、§4.2のCPL算出ルールと同じ考え方）。会社全体の予算・反響数目標も、拠点別＋全社共通の値を自動合算して算出するのみで、独立した値としては持たない（内訳との不整合を防ぐため）。
- **年間予実ビュー（2026-08-27確認・新規）**: 上記の年間グリッドと同じ軸（会社全体KPI／チャネル別）で、目標と実績を12ヶ月分並べて比較できる読み取り専用の画面を設ける。達成状況（反響数・来場等は実績が目標以上、費用・単価は実績が目標以下で達成）に応じて表示を強調する。

#### 4.4.1 施策マスタのクライアント別有効/無効管理（2026-08-27確認・新規）

- §4.2.3 のクライアント固有施策の追加に加えて、**デフォルト施策17件それぞれについて、クライアントごとに「使用する/しない」を切り替えられる**（`client_channel_settings`、§6）。無効化した施策は、施策データ入力・チャネル別内訳・上記のチャネル別目標・予算グリッドから除外される（過去に記録済みの`campaign_metrics`等のデータやレポートスナップショットには影響しない）。
- クライアント固有施策についても、追加だけでなく編集・無効化ができる（`campaign_channels.enabled`、§6）。無効化は既存データとの参照整合性を保つため、行を削除せず非表示にする方式とする。
- いずれの操作も代理店担当者のみが行える（§4.2.3の既存方針を維持）。

### 4.5 ダッシュボード

選択中のクライアント（代理店側は切り替え、住宅会社側は自社固定）・指定期間について、以下を表示する。

- **ファネル図**（最優先）: 施策 → 反響 → 来場予約 → 来場 → 見積もり／図面出し → 契約、の各段階の件数を表示する。起点の「施策」段階は`campaign_metrics`上に件数として持てるカラムが無いため、**チャネルごとの反響数を多い順に並べた内訳リストとして表示する**（2026-08-10確認）。見積もり・図面出しは来場から分岐する並列の2段階として表示し（件数の合算・重複排除は行わない、§3）、遷移率は「反響→来場予約」「来場予約→来場」「来場→見積もり」「来場→図面出し」「来場→契約」をそれぞれ来場数（または前段階の件数）を分母として算出する。
- 期間推移グラフ: 主要 KPI の月次／週次推移。
- チャネル別内訳: 施策ごとの反響数・費用等の内訳。広告チャネルについては、クリック率 (CTR)・クリック単価 (CPC)・反響あたりの費用 (CPL) をあわせて表示する（§4.2 算出式のとおり、表示時に算出）。運用（オーガニック）チャネルのフォロワー数・流入率の集計ルールは §6「指標ごとの集計方法」のとおり（フォロワー数は最新値採用、流入率は集計せず入力粒度のまま表示）。クライアント固有の追加施策（§4.2.3）も同じ内訳表に含める。**チャネルごとに予算・消化率（実績費用÷予算）も表示する（2026-08-27確認・§4.4.1同様）**。
- **制作・クリエイティブ費用**（2026-08-10確認）: §4.2.4 で入力した項目の対象期間合計金額を表示する。
- 予実対比: 目標値と実績値の対比。**目標は会社全体に対してのみ設定するため（§4.4）、予実対比も会社全体の実績（拠点別データ＋全社共通データの合算）に対して行う。拠点別の予実対比は v1 では行わない。** 反響数・予算についても同様に、チャネル別目標（§4.4）を拠点別＋全社共通で合算した会社全体の値と実績を対比する（2026-08-27確認）。
- 拠点別内訳: 拠点を登録しているクライアントの場合、拠点ごとの内訳を表示できる。**拠点に紐づかないデータ（全社共通）は「全社共通」という区分として内訳にあわせて表示し、内訳の合計（各拠点＋全社共通）が会社全体の合計と一致するようにする。** 拠点を登録していないクライアントの場合、この内訳セクション自体を表示しない（2026-08-10確認）。
- **期間比較（決定済み）**: 選択中の期間（基準期間）に加えて、任意の比較期間をもう1つ指定できる（期間種別＝月次・週次は基準期間と同じものを選ぶ）。ファネル各段階の件数、制作・クリエイティブ費用の合計、チャネル別内訳、拠点別内訳の各数値について、基準期間の値・比較期間の値・差分（実数）・増減率（%）を並べて表示する。フォロワー数は§6の集計ルール（期間末時点の最新値）に基づく値同士を比較する。流入率は§6のとおり集計しないため比較表示の対象外とする。予実対比（目標との対比）には適用しない（目標は単一期間に対する値のため）。チャネル別内訳の比較表示は、施策数×指標数が多くなり列数が破綻しやすいため、主要指標（費用・反響数・CPL）に絞って表示してよい（2026-08-10確認）。

### 4.6 レポート閲覧・エクスポート

- **期間を指定して**（月次・週次・任意の開始日〜終了日を指定するカスタム期間のいずれも選べる、2026-08-10確認：対象月の単一選択から変更）、§4.5 のダッシュボード内容をまとめたレポートを生成する。
- **レポート生成時に、§4.5の期間比較と同様に任意の比較期間を含めるかどうかを選択できる**（2026-08-10確認）。比較期間を含めた場合、期間比較の集計結果もスナップショットに含める。
- **生成した時点のファネル・チャネル別・制作費用合計・拠点別・予実の集計結果（比較期間を含める場合は期間比較の結果も）はスナップショットとして保存する**（決定済み）。生成後に元データ（施策データ・来場〜契約データ・目標値）が修正されても、生成済みのレポートの内容は変わらない。
- レポートは画面上でいつでも閲覧できるほか、PDF としてダウンロードできる（クライアント提出用）。PDF はスナップショットのデータから都度描画し、ファイル自体は永続保存しない（§6）。
- クライアントごとに、過去に生成したレポートの一覧（生成日時・対象期間・比較期間の有無）を確認し、再度開ける。

- **認証との紐付け**: `agency_users.id` / `client_users.id` は Supabase Auth の `auth.users.id` をそのまま主キーとして使う（サインアップ/招待時に auth ユーザーを作成し、同じ id でプロフィール行を作成する）。RLS ポリシーは `auth.uid()` がこれらのテーブルの `id` と一致するかどうかで判定する。`agency_users` は Google OAuth コールバック時に Service Role 経由で自動作成（ドメイン一致確認後、RLS の `agency_users_insert` ポリシーは `is_agency_user()` 前提のため初回作成時は通せず Service Role が必須、§4.1.1）。`client_users` は招待（`admin.inviteUserByEmail`）実行と同じサーバー処理内で作成する。
- **RLS**: `clients` 配下の全テーブルは、`auth.uid()` が `agency_user_clients` 経由で割当のある代理店ユーザー、または該当 `client_id` に属する住宅会社ユーザー（`client_users.client_id` が一致）である場合のみ読み書き可。他クライアントのデータには一切アクセスできない。
- **算出指標（CTR・CPC・CPL）**: クリック率・クリック単価・反響あたりの費用（§4.2, §4.5）は `campaign_metrics` にカラムを持たず、集計後の `impressions` / `clicks` / `cost` / `leads` から表示時に算出する。分母が 0 の場合は算出不可として扱う。
- **チャネル別目標・予算・想定単価（§4.4、2026-08-27新規）**: `campaign_targets` は `target_leads`（反響数目標）・`budget_amount`（予算）のみを保持し、想定単価（想定CPL）にはカラムを持たない。想定単価＝ `budget_amount` ÷ `target_leads` を表示のたびに算出する（分母が0または未入力の場合は算出不可）。会社全体の合計反響数目標・会社全体予算も同様に、`campaign_targets` の拠点別＋全社共通（`location_id` が null）の行をすべて合算して表示のたびに算出する（保存しない）値であり、独立したカラム・行としては持たない（`targets` から `kpi_key='leads_total'` を廃止したのはこのため）。
- **期間比較（§4.5）**: 比較値・差分・増減率は保存せず、基準期間・比較期間それぞれについて通常の集計クエリ（§6「指標ごとの集計方法」に従う）を実行し、表示時にその場で差分計算する。
- **入力項目の必須・任意（§4.2.3）**: `campaign_channels.enabled_fields` / `required_fields` によりチャネルごとに入力項目とその必須・任意を制御する。TVCM・ポータルサイト・チラシ折込チャネルは `enabled_fields` に `impressions`/`clicks` を含むが `required_fields` には含めない（任意項目）。その他の広告チャネル・クライアント固有の追加施策は、選択した `enabled_fields` の中で `cost` のみを必須とする（§4.2.3）。
- **チャネル別内訳の表示ロジック（§4.5）**: CTR/CPC/CPL・フォロワー数・流入率の列は、チャネルの種別（広告/運用）で表示・非表示を切り替えるのではなく、常に算出を試みる。該当項目が入力されていない（nullの）場合は自然に「-」表示になるため、`enabled_fields` の組み合わせが異なるクライアント固有の追加施策でも同じ表示ロジックで対応できる。
- **施策の有効/無効判定（§4.4.1、2026-08-27新規）**: 施策データ入力・チャネル別内訳・チャネル別目標グリッドに表示する施策一覧は、次のルールで絞り込む。クライアント固有施策（`campaign_channels.client_id` が非null）は `enabled` カラムで判定する。デフォルト施策（`client_id` が null）は `client_channel_settings` に該当クライアント・チャネルの行があればその `enabled` 値、無ければ true（使用する）とみなす。無効化は表示上のフィルタであり、既存の `campaign_metrics` / `campaign_targets` データやレポートスナップショットには影響しない。
- **制作・クリエイティブ費用（§4.2.4）**: `production_costs` は施策（`campaign_channels`/`campaign_metrics`）と紐づかない独立したコスト記録であり、CTR/CPC/CPL等の算出には含めない。ダッシュボード・レポートでは期間合計のみを表示する。
- **拠点集計のルール**: `campaign_metrics` / `funnel_metrics` / `campaign_targets` の `location_id` が null の行は「全社共通」を表す。会社全体の合計値は、特定拠点（`location_id` が非 null）の行と全社共通（`location_id` が null）の行を**すべて合算**して算出する（§3）。
- **指標ごとの集計方法（決定済み）**: 指標の性質によって、期間・拠点をまたぐ集計方法を分ける。
  - **フロー指標**（`cost` / `impressions` / `clicks` / `leads` / `posts` / `views` / `visit_reservations` / `visits` / `estimates` / `floor_plans` / `contracts`）: 期間・拠点をまたいで単純合算する。週次データを月次実績として集計する場合、月をまたぐ週（例: 4/29〜5/5の週）は日数比率で按分し、各月にその比率分を加算する（例: 7日中3日が4月・4日が5月なら、実績値を 3/7・4/7 の比率で両月に配分する）。
  - **ストック指標**（`followers`）: 合算しない。対象期間の末日に最も近い入力値を採用する（週次データを月次実績として扱う場合も、月内で最新の入力値をその月のフォロワー数とする）。拠点をまたぐ集計（会社全体・拠点別内訳）は、各拠点・全社共通それぞれの最新値を合算する（独立したアカウントを持つ前提）。
  - **比率指標**（`inflow_rate`）: 集計しない。入力された粒度（拠点・期間ごと）のままダッシュボード・レポートに表示し、複数拠点・複数期間をまたいだ代表値は算出しない。
- **一意性制約**: `campaign_metrics` は `(client_id, location_id, channel_id, period_type, period_start)`、`funnel_metrics` は `(client_id, location_id, period_type, period_start)`、`targets` は `(client_id, kpi_key, period_start)`、`campaign_targets` は `(client_id, location_id, channel_id, period_start)`、`client_channel_settings` は `(client_id, channel_id)` の組み合わせで UNIQUE 制約（`campaign_targets` は `campaign_metrics` と同様に `location_id` の有無で部分ユニークインデックスを分ける）を設ける（§6 スキーマ参照）。API 連携行の同期は、この制約に対する upsert として実装する。
- **編集履歴の記録**: `locations` / `campaign_metrics` / `funnel_metrics` は `created_by_type` / `created_by_id`（作成者）と `updated_by_type` / `updated_by_id`（最終更新者）を持ち、`'agency'` か `'client'` のどちら側が登録・編集したかを追跡できるようにする（§4.1, §4.2.1, §4.3）。`campaign_metrics` の `manually_overridden` が true になった行は、その時点の `updated_by_type` / `updated_by_id` が上書きした担当者を示す。
- **`ad_connections` のトークン**: `access_token` / `refresh_token` は暗号化して保存し、アプリケーション層（Service Role 経由）以外からは参照できないようにする。
- **コンバージョンアクションの選択**: 同期処理は `ad_connections.tracked_conversion_action_ids` に含まれるコンバージョンアクションの合算値を `campaign_metrics.leads` として書き込む（§4.2.2）。担当者が選択を変更した場合、変更以降に実行される同期（自動・手動とも）から新しい選択が適用される。
- **`platform_integrations`（フェーズドロールアウト）**: 媒体（Google広告・Yahoo広告・Meta広告）ごとの API 審査状況を保持する。`status = 'pending_review'` の間は、接続画面の OAuth 接続操作を非活性にし「審査待ち」を表示、当該チャネルは手動入力のみで運用する。`status = 'active'` になった後にクライアント側の OAuth 接続が完了するまでの間も、同様に手動入力で運用を継続する（§4.2.2）。
- Storage: v1 では画像・ファイルの保存要件なし（PDF レポートは都度生成・都度ダウンロードとし、永続保存はしない）。

## 7. 技術スタック

- フロント/サーバー: **Next.js (App Router)** / TypeScript
- DB・認証: **Supabase**（Postgres + Auth + RLS）
- ホスティング: **Vercel**
- スタイル: Tailwind CSS
- 認証: Supabase Auth。代理店ユーザーは自社 Google Workspace ドメイン限定の Google OAuth（ドメイン一致で初回ログイン時に自動発行、招待不要）、住宅会社ユーザーはメール + パスワードのアカウント発行制（招待リンクからパスワード設定）。代理店ユーザー／住宅会社ユーザーをそれぞれ別テーブルで管理し、RLS でスコープを分離（§4.1.1決定）
- グラフ描画: **Recharts**（決定済み）。ファネル図（§4.5）は Recharts の基本チャートに加え、遷移率表示等はカスタム SVG／独自コンポーネントで補う。
- PDF 生成: **サーバーサイド HTML→PDF 変換**（決定済み）。Vercel の Serverless Function 上で Puppeteer（または Playwright）等を用いてレポート画面の HTML を PDF 化する。ファイル自体は永続保存せず、ダウンロード要求のたびにスナップショットデータ（§6 `reports.snapshot_data`）から都度描画する。
- 広告 API 連携（§4.2.2）: **Google Ads API**・**Yahoo!広告 API**・**Meta Marketing API** と OAuth2 で接続する。
- 定期同期のスケジューリング: **Vercel Cron Jobs**（決定済み）で日次バッチを実行し、`ad_connections` の各接続について同期処理を呼び出す。

## 8. 非機能要件

- **レスポンシブ**: 管理画面は PC 利用が中心だが、入力担当者がスマホから入力する可能性も考慮し、モバイル表示にも対応する。
- **データ正確性**: 手動入力が前提のため、必須項目チェック・数値バリデーション（負数不可等）を行う。
- **パフォーマンス**: 蓄積データ量が増えても、期間集計・グラフ描画が実用的な速度で表示されること。
- **セキュリティ**: RLS により、クライアントは自社データのみ、代理店は割当のあるクライアントのみアクセス可能とする。広告アカウントの OAuth トークンは暗号化して保存する。
- **外部 API 連携の耐障害性**: Google広告・Yahoo広告・Meta広告の API 障害・認証切れ・レート制限が発生しても、当該クライアントの他機能（手動入力・閲覧等）に影響しないようにする。同期エラーは接続状態として画面に表示する（§4.2.2）。
- **可用性**: Supabase 標準のバックアップ・冗長性に準拠する。

- 制作・クリエイティブ費用は施策（反響）とは独立した項目名＋金額の自由入力リストとして`production_costs`に記録し、CTR/CPC/CPL等の算出には含めない。ダッシュボード・レポートには期間合計のみ表示する（§4.2.4、2026-08-10確認）。
- レポートは対象月の単一選択ではなく、月次・週次・カスタム（任意の開始日〜終了日）の期間指定に対応する。生成時に比較期間を含めるかどうかを選択でき、含めた場合は期間比較の集計結果も`reports.snapshot_data`に保存する（§4.6、2026-08-10確認）。
- 目標・予算は「KPI（またはチャネル）×12ヶ月」の年間グリッドで一括入力・編集できる。グリッドの起点月はクライアントごとに設定する事業年度の開始月（`clients.fiscal_year_start_month`、デフォルト4月）に従う（§4.4、2026-08-27確認）。
- 反響数の目標・予算はチャネル別（拠点別＋全社共通）に`campaign_targets`で管理し、想定単価（想定CPL）＝予算÷反響数目標を表示のたびに算出する。会社全体の合計反響数・会社全体予算は、拠点別＋全社共通の値を自動合算した表示専用の値とし、独立した値としては持たない（§4.4・§6、2026-08-27確認）。
- デフォルト施策17件は、クライアントごとに「使用する/しない」を`client_channel_settings`で切り替えられる。クライアント固有施策も追加だけでなく編集・無効化（`campaign_channels.enabled`）ができる。いずれも代理店のみが操作できる（§4.4.1、2026-08-27確認）。
- 目標・予算の年間グリッドと同じ軸（会社全体KPI／チャネル別）で、目標と実績を12ヶ月分並べて比較できる読み取り専用の年間予実ビューを設ける（§4.4、2026-08-27確認）。
- クライアントは、内部PK（`clients.id`）とは別に、外部アプリ連携用の識別子（`clients.external_client_id`）を持つ。代理店が任意入力・編集できる（未設定可、重複不可）。クライアント登録画面・一覧画面の両方で入力・編集できる（§4.1、2026-08-27確認）。

## 11. 受け入れ基準（v1 完了の定義）

- [ ] 代理店担当者が新規クライアントを登録し、住宅会社側の初期アカウントを発行できる
- [ ] 代理店担当者がクライアントの外部連携ID（`external_client_id`）を登録画面・一覧画面から入力・編集でき、他クライアントと重複する値は設定できない
- [ ] 代理店・住宅会社どちらからも拠点を登録・編集できる
- [ ] 代理店担当者が担当クライアントを切り替えて、各クライアントのダッシュボードを閲覧できる
- [ ] 代理店担当者が施策（広告／運用オーガニック）データを、期間・拠点を指定して手動入力できる
- [ ] 代理店担当者がクライアントごとに施策マスタへ独自の媒体を追加でき、使用する入力項目をチェックボックスで選択できる
- [ ] 代理店担当者が制作・クリエイティブ費用を項目名・金額で入力でき、ダッシュボード・レポートで期間合計を確認できる
- [ ] 接続画面に媒体（Google広告・Yahoo広告・Meta広告）ごとの審査状況（審査待ち／連携可能）が表示され、審査待ちの媒体は OAuth 接続操作ができず、手動入力のみで運用できる
- [ ] 審査完了済みの媒体について、代理店・住宅会社どちらの画面からも、広告アカウントを OAuth 接続できる
- [ ] 接続済みの広告アカウントから、費用・表示回数・クリック数・反響数が日次で自動同期され、「今すぐ同期」でも即時取得できる
- [ ] 接続した広告アカウントについて、反響数としてカウントするコンバージョンアクションを一覧から選択（複数選択可）でき、選択に応じた合算値が反響数として同期される
- [ ] API 連携で取得したデータを手動で上書き修正でき、上書き済みの行は次回の自動同期で上書きされない
- [ ] 住宅会社担当者が来場予約・来場・見積もり・図面出し・契約データを、期間・拠点を指定して入力できる
- [ ] 代理店担当者がクライアントごとに月次 KPI 目標（来場予約数・来場数・契約数）を年間グリッドで一括設定できる
- [ ] 代理店担当者がクライアントごと・拠点ごとにチャネル別の反響数目標・予算を年間グリッドで一括設定でき、想定単価（想定CPL）が自動表示される
- [ ] 代理店担当者がクライアントごとにデフォルト施策の使用/不使用を切り替え、クライアント固有施策を編集・無効化できる
- [ ] 年間予実ビューで、会社全体KPI・チャネル別の目標と実績を12ヶ月分並べて確認できる
- [ ] ダッシュボードで、施策→反響→来場予約→来場→見積もり／図面出し→契約のファネル図（件数・遷移率）が表示される
- [ ] ダッシュボードで、目標と実績の予実対比が表示される
- [ ] ダッシュボードで、任意の2期間（基準期間・比較期間）を指定して、主要指標の差分・増減率を比較表示できる
- [ ] 期間（月次・週次・カスタム）を指定し、必要に応じて比較期間を含めてレポートを生成でき、画面閲覧および PDF ダウンロードができる
- [ ] 生成済みレポートはスナップショットとして保存され、生成後に元データが修正されても内容が変わらない
- [ ] クライアントごとに、過去に生成したレポートの一覧から再度開ける
- [ ] 拠点を登録しているクライアントについて、拠点別の内訳（各拠点＋全社共通）が確認でき、その合計が会社全体の数値と一致する

## 12. デザイン方針

**`docs/DESIGN_SYSTEM.md`（社内ツール共通デザインシステム）を本プロダクトのデザインベースとする（決定済み）。** 画面実装時は、機能要件（本書）と合わせて DESIGN_SYSTEM.md を必ず参照する。

### 12.1 技術スタックの違いに関する注記

DESIGN_SYSTEM.md は素の HTML/CSS/JS 実装（PHP プロジェクト）を前提に書かれているが、本プロダクトは **Next.js + Tailwind CSS**（§7）。そのため同ドキュメント §7 の CSS はそのままコピーせず、以下のように翻訳して踏襲する。

- カラートークン・角丸・シャドウ（DESIGN_SYSTEM.md §1, §3）→ `tailwind.config` の `theme.extend.colors` / `borderRadius` / `boxShadow` に設定する。
- タイポグラフィ（§2）→ `tailwind.config` の `fontFamily` に Noto Sans JP／Archivo を設定する（`next/font` 等でのフォント読み込みに置き換える）。
- レイアウトシェル・各コンポーネント（§4, §5）→ 共通の React コンポーネント（例: `Sidebar` / `PageHeader` / `Button` / `Panel` / `Tag` / `FilterBar`）として実装し、素の HTML テンプレートではなくコンポーネント単位で使い回す。
- 実装のふるまい・レスポンシブ挙動（サイドバーのハンバーガー変形、モバイルでの縦積み等、§4.1）はそのまま踏襲する。

### 12.2 採用する内容

- **カラーパレット**: DESIGN_SYSTEM.md §1 のトークンをそのまま採用する（決定済み）。`--navy: #0F2E4F` を基調、`--accent: #A61A72`（マゼンタ）をアクセントとし、グレースケール・`--danger` も共通のまま使う。
- **タイポグラフィ**: Noto Sans JP（本文）＋ Archivo（英字ラベル・eyebrow・ロゴ）。基本文字サイズ 13px（§2）。
- **レイアウト**: 左サイドバー（240px・ネイビー背景）＋ メインコンテンツ。768px 以下でサイドバーが上部バー＋ハンバーガーメニューに変形する（§4, §4.1）。サイドバーのロゴ・サブテキストは本プロダクト名（現状は仮称、§1・§10）に置き換える。
- **コンポーネント**: ページ見出し・ボタン・フォーム・フィルターバー・テーブル・タグ/バッジ・パネル/カード・ログイン画面（§5.1〜5.9）のパターンをそのまま踏襲する。`/login`（§5）は §5.9 のネイビー背景＋中央カードのパターンとする。
- **原則**: 「デザインは実装済みの機能に合わせる。参考デザインにあっても本書（spec.md）にない機能・要素は実装しない」という DESIGN_SYSTEM.md §0 の方針をそのまま踏襲する。

### 12.3 本プロダクト固有の新規コンポーネント

ファネル図・期間推移グラフ・チャネル別内訳・予実対比・期間比較（§4.5）は、名刺管理ツール由来の DESIGN_SYSTEM.md には存在しないパターンのため新規に設計する。ただし色・角丸・シャドウ・情報密度のトーン（§12.2 のトークン）には揃える。グラフ描画（Recharts、§7）の配色は、彩度を抑えたセットを基本としつつ `--navy` / `--accent` と調和させる。

### 12.4 確認手順

実装後は DESIGN_SYSTEM.md §6 の手順に準じ、Headless Chrome 等で実際にスクリーンショットを取得し、PC 幅・スマホ幅（375〜390px 程度）の両方で見た目を確認してから完了とする（§8 非機能要件のレスポンシブ要件とも整合させる）。
