## 0. 総括：最大の課題は「1施策=1画面」の施策データ入力

このツールの最重要要件（spec §1）は「施策→反響→…→契約のファネルを、住宅会社・代理店が分担入力しながら1つのダッシュボードに統合して見られること」であり、**入力の分担と閲覧の統合の両立が品質の核**とspec自身が明言している。にもかかわらず、現状もっとも入力頻度が高い「施策データ入力」（`/agency/clients/[id]/campaigns`）が、初期施策マスタ17件＋クライアント固有施策の分だけ**1件ずつ別ページに遷移して編集する**方式になっており、月次更新のたびに代理店担当者が最大20回近いページ往復を強いられる。

さらに興味深いのは、**この問題は2026-08-10のUIモックアップ検証で一度解決されていた**という点。モックアップ実装（`CampaignsView.tsx`）では一覧の各行に「修正」ボタン→モーダルでその場編集、という手間の少ない方式に到達していた（masterplan.mdに明記）。しかしPhase 5で実データ接続版を作った際、このモーダル方式は移植されず、`/campaigns/entry` という別ページへの遷移方式に後退している。

→ **§1-1で詳述。改善提案の中で最優先。**

## 1. 全体を貫く「入力の手間」の課題

### 🔴 1-1. 施策データ入力が「1施策=1画面遷移」（`campaigns/page.tsx` → `campaigns/entry/page.tsx`）

- **現状**：一覧テーブルの各行に「入力／編集」リンクがあり、クリックすると当該1施策・1期間・1拠点のみを扱う別ページに遷移する。保存すると一覧に戻る。これを施策数分（初期17件＋クライアント固有分）繰り返す。
- **本来あるべき姿との差分**：2026-08-10のモックアップでは「一覧の行→モーダルでその場編集」に到達済みで、ページ遷移が発生しない。実データ版はこれより手間が多い。
- **影響**：月次更新のたびに代理店担当者が施策数分のページ往復をする。API連携3媒体（Google/Yahoo/Meta）が有効になれば対象は手動施策のみに絞られるが、v1時点では審査待ちのため実質17施策すべてが手動運用（§4.2.2フェーズドロールアウト）。当面はこの手間がフルにのしかかる。
- **改善案（段階的）**：
  1. **最小コスト**：モックアップで実装済みの「一覧行→モーダル編集」パターンを実データ版に移植する（`Modal.tsx`は既存資産、`CampaignsView.tsx`の`openEdit`/`saveEdit`ロジックを流用可能）。
  2. **理想形**：施策一覧をスプレッドシート風に「行＝施策、列＝入力項目」の一括編集テーブルにし、複数施策の数値を1画面でまとめて入力→1回の送信で保存する。表示回数・クリック数など施策ごとに有効な列が異なる点（§4.2.3 enabled_fields）は、無効な列をグレーアウト／非表示にすれば両立できる。
  3. API連携施策（source='api'）は基本読み取り専用表示にし、上書きしたい時だけ編集可能にすることで、「手動で埋めるべき施策」を視覚的に絞り込めるようにする。

### 🔴 1-2. 来場・見積もり・図面出し・契約の入力が3画面に分断され、期間・拠点選択をやり直す

- **現状**：`/client/visits`・`/client/proposals`・`/client/contracts` はそれぞれ独立ページで、「期間種別／対象月・週開始日／拠点」の選択フォームを個別に持つ。同じ期間・拠点に対して3つとも入力する場合、毎回選び直しが必要（URLクエリやセッションで引き継がれない）。
- **技術的背景**：3画面とも実体は同じ`funnel_metrics`行の異なるカラムを更新するだけ（masterplan Phase 7参照）なので、1画面へ統合しても設計上の障害はない。
- **改善案**：
  - 本命：来場予約数・来場数・見積もり数・図面出し数・契約数を1つのフォーム（1画面）にまとめる。ラベル分割（例：パネルを「来場」「商談」「契約」に分けつつ同一フォーム）で情報の性質差は保てる。
  - 次善：画面を分けたままでも、ページ遷移時に現在の期間・拠点クエリを自動的に引き継ぐ（サイドバーや画面内リンクに`?periodType=...&periodMonth=...&locationId=...`を付与）。

### ✅ 1-3. レポート生成・期間選択フォームで、無関係な入力欄が常に全部表示される（2026-08-27実装済み）

- **現状（旧）**：`RealReports`のレポート生成フォーム、`RealDashboard`のダッシュボード期間選択、`campaigns`/`visits`等の期間選択、いずれもサーバーコンポーネントの素の`<select>`+`<input>`群のため、「期間種別＝月次」を選んでいても、週次用の「週の開始日」欄・カスタム用の「開始日〜終了日」欄が常時表示されたまま消えなかった。
- **影響**：ユーザーは「今回はどの欄を埋めればよいか」を毎回判断する必要があり、誤って無関係な欄に値を入れてしまうリスクがある（特にレポート生成は月次/週次/カスタム/比較の組み合わせで最大6欄が同時表示）。
- **実装済み（2026-08-27、4セッション目）**：改善案通り、該当フォームのみ軽量にクライアントコンポーネント化した。
  - `src/components/forms/PeriodTypeFields.tsx`（新規）：月次/週次の2択で使う汎用コンポーネント。`campaigns/page.tsx`・`client/visits`・`client/proposals`・`client/contracts`の4画面すべての「期間・拠点を選択」フォームに適用。
  - `src/components/reports/ReportGenerateForm.tsx`（新規）：月次/週次/カスタムの3択＋比較期間トグルを扱うレポート専用コンポーネント。基準期間の種別に応じて対応する1欄のみ表示し、「比較期間を含める」がオフの間は比較欄自体を非表示にする（最大6欄→最小1欄に削減）。`RealReports.tsx`（代理店・住宅会社どちらの`/reports`からも共有）に適用。
  - `src/components/dashboard/DashboardPeriodForm.tsx`（新規）：ダッシュボードの「期間比較を表示する」チェックがオフの間は比較期間欄を非表示にする。`RealDashboard.tsx`に適用。
  - `campaigns/entry`ページ（期間種別を選ぶUIを持たず、既に決まった期間をhiddenフィールドで引き継ぐだけ）は対象外。
  - 検証：`npx tsc --noEmit`・`npm run lint`・`npm run test`（33件）・`npm run build`すべて成功。

### 🟡 1-4. 「未入力」と「0」の区別がつかない

- **targets（目標設定）**：空欄で保存すると「未設定に戻す」という仕様（masterplan Phase 8で確定）自体は妥当だが、画面上は「一度も入力していない月」と「過去に空欄保存で未設定にした月」の見分けがつかない。
- **visits（来場入力）**：`defaultValue={existing?.visit_reservations ?? 0}` のため、未入力の期間を開いてもフォームには"0"が最初から入っている。担当者が数値を変更せずうっかり保存すると、その期間の実績が「0件」として確定してしまう（本当は「まだ入力していないだけ」の可能性がある）。
- **改善案**：未入力時は空欄＋プレースホルダー「未入力」で表示し、`0`と`未入力`を明確に区別する。一覧・ダッシュボード側でも「未入力の期間・施策・拠点」をハイライトできるとなお良い（§2-6参照）。

## 2. ダッシュボード（`/agency/clients/[id]/dashboard`, `/client/dashboard`）

### 🟡 2-1. Panelが7つ以上縦に並び、目的の情報にたどり着くまでのスクロールが長い

- 期間選択／ファネル図／期間推移／チャネル別内訳／制作費用／予実対比／拠点別内訳／期間比較、の順に単純に縦積み。ページ内ジャンプやタブ切り替えが無い。
- 改善案：ページ上部にセクションへのアンカーリンク（概要・チャネル・拠点・比較）を設置する、または「概要／詳細」の2段構成にしてスクロール量を減らす。

### 🟡 2-2. 予実対比（`TargetVsActual`）が達成率を色で表現していない

- 達成率(%)はテキストでは出るが、進捗バーは常にnavy一色。未達（例：50%未満）と達成（100%以上）が視覚的に同じ見た目になっている。
- 改善案：達成率に応じてバー色を変える（未達=警告色、達成=成功色など）。数値の羅列より一瞬で状況を把握できるようにする。

### 🟡 2-3. チャネル別内訳テーブルが10列あり、モバイルは常時横スクロール

- 施策/費用/表示回数/クリック数/反響数/CTR/CPC/CPL/フォロワー数/流入率の10列。施策数が多いクライアントでは縦にも長くなり、月次比較の際に目的の行を探しづらい。
- 改善案：デフォルト表示を主要指標（費用・反響数・CPL）に絞り、詳細列は行を展開/トグルで表示する。あるいは反響数の多い順など簡易ソートを提供する。

### 🟢 2-4. 期間比較の切り替えがチェックボックス1つで、ページが縦に倍近く伸びる

- 頻繁に使う想定の機能（spec §4.5「決定済み」）にしては発見性が低く、オンにした際のレイアウト変化が大きい。
- 改善案：比較専用のタブ、または画面上部に固定した切替UIにする。あわせて、住宅業界特有の季節性を考えると「前月」だけでなく「前年同月」への切り替えショートカットがあると実務的。

### 🟢 2-5. ファネル図の「施策別反響数」ボックスが施策数分だけ縦に伸び、ファネル本体とのバランスが悪い

- 17施策＋クライアント固有施策すべてに反響があると、幅200pxの箱に十数行が並ぶ。横並び4ボックスのファネル本体に対して視覚的に不釣り合い。
- 改善案：上位5〜6件＋「その他」でまとめる、または横棒グラフ化する。

### 🟡 2-6. 「今月まだ何を入力すべきか」がダッシュボードから分からない

- 予実の実績値が0や空欄でも、それが「未入力」か「本当に0件」か区別できない（§1-4と関連）。代理店・住宅会社どちらの担当者も、ダッシュボードを見ただけでは今月の入力漏れに気づけない。
- 改善案：「未入力の施策・拠点」を警告表示するセクション、または入力完了率の簡易インジケーターを追加する。

### 🔴 2-7. 年間を通じて「目標×実績」を並べて確認できる画面が存在しない（2026-08-27ユーザー指摘）

- **現状**：ダッシュボードの「予実対比」（`TargetVsActual`）は選択中の1期間のみのバー表示で、年間を通じた達成状況の一覧性がない。「期間推移」（`TrendChart`）は直近6ヶ月の実績の折れ線のみで、目標値のオーバーレイも費用（予算・実績費用）も無い。両者とも、§4-1・§9-1で作った「年間グリッド（KPI・チャネル×12ヶ月）」と同じ軸で年間の目標と実績を並べて見比べる画面ではない。
- **背景**：住宅業界は月によって繁閑差が大きく、「今年はどの月が目標割れしていたか」を一覧で振り返る需要が強い。目標入力（§4-1・§9-1）を年間グリッドで一括入力できるようにするなら、対になる「年間予実ビュー」（読み取り専用）があると一貫性が取れる。
- **提案する設計**：目標・予算の入力グリッド（§9-1のタブ構成）と同じ行・列構造で、各セルに「目標」（小さくグレー）と「実績」（太字・達成/未達で緑・赤に色分け）を並べて表示する読み取り専用グリッドを追加する。
  - 会社全体KPI：来場予約数・来場数・契約数・合計反響数の4行×12ヶ月。実績が目標以上なら緑、未満なら赤。
  - チャネル別：反響数・予算(と実績費用)・単価(目標CPLと実績CPL)の3行1セット×チャネル数×12ヶ月。反響数は「実績が目標以上で緑」、予算・単価は「実績が目標以下で緑（使いすぎ・単価上振れは赤）」という逆方向の判定になる点に注意。
  - 配置は目標・予算画面の3つ目のタブ（「年間予実」）として置くのが実装コスト・情報の近さの両面で自然。ダッシュボード側にも縮小版（会社全体KPIの4行のみなど）を出せるとより良い。
  - 2026-08-27、上記コンセプトをモック（`src/app/dev-preview/targets-budget/page.tsx`）の3つ目のタブとして実装・確認済み（詳細は§9-1参照）。

## 3. 施策データ入力（`/agency/clients/[id]/campaigns`）

（§1-1で最重要点は既述。以下は追加で見つかった点）

### 🟡 3-1. 施策一覧テーブルに表示回数・クリック数列がない

- 一覧には「施策／費用／反響数／CTR／CPC／CPL」のみ表示。CTR/CPCが「-」の場合、表示回数・クリック数が未入力なのか、算出不能（分母ゼロ）なのかが一覧からは判別できない。
- 改善案：表示回数・クリック数も列に追加する（DESIGN_SYSTEM方針どおり横スクロールで対応）。

### 🟡 3-2. 広告アカウント接続パネルが常に最上部に表示され、日常業務（数値入力）より目立つ

- 通常は月1回程度しか触らない「接続管理」が、毎回見る「施策データ入力」より視覚的優先度が高い配置になっている。
- 改善案：エラー・審査待ちなど異常時のみ目立たせ、正常時は折りたたみ表示にする。

### ✅ 3-3. 施策マスタが「クライアント固有施策の追加のみ」で、デフォルト17施策の要否をクライアントごとに調整できない（2026-08-27ユーザー提案・実装済み）

- **現状**：`campaign_channels`のデフォルト17件（`client_id`が null）は全クライアントに一律で適用される。クライアントごとに「このクライアントはTVCM・Pinterestはやらない」を選べず、施策データ入力・チャネル別内訳・§9-1で追加した「チャネル別計画」グリッドなど、あらゆる画面に使わない施策の行が並んでしまう。加えて、クライアント固有施策は追加はできるが編集・削除（無効化）ができない（masterplan既知の制限）。
- **影響**：施策数が多いクライアント一覧・グリッドほど、不要な行のスクロール・視認性の悪化が大きくなる。§9-1の「チャネル別計画」グリッドは1施策につき3行を占めるため、この問題の影響を特に強く受ける。
- **確定した設計（2026-08-27、`supabase/migrations/0004_channel_targets_budget_and_settings.sql`で実装）**：
  - クライアントの施策マスタ管理画面（`/agency/clients/[id]/campaigns`の「施策の有効/無効管理」パネル）で、デフォルト17件それぞれに「使用する/しない」のトグルを持たせる（**2026-08-27実装済み**）。
  - クライアント固有施策も同じ画面で無効化できるようにする（**実装済み**。編集(名称・入力項目の変更)は既存の追加フォームと別UIになるため、今回はスコープ外のまま）。削除は既存データとの整合性を考え、ハードデリートではなく「無効化」に倣う。
  - データ設計：新しい対応表 `client_channel_settings`（`client_id`, `channel_id`, `enabled` boolean、デフォルト`true`）で、デフォルト施策のクライアント単位の有効・無効を上書き管理する。デフォルト施策自体（`client_id` is null の行）は共通のまま変更しない設計にし、既存の`campaign_metrics`等の参照整合性に影響を与えない。クライアント固有施策の無効化は、既存の`campaign_channels`に追加した`enabled`列（デフォルト`true`）で管理する。
  - 無効化された施策は、入力フォーム・チャネル別内訳・チャネル別計画グリッドから除外されるが、過去に記録された`campaign_metrics`データやレポートスナップショットは影響を受けない（表示上のフィルタであり、データ削除ではない）。**2026-08-27実装済み**：判定ロジックを`src/lib/campaigns/channelVisibility.ts`に共通化し、上記3箇所すべてで反映されることを確認済み（`npx tsc --noEmit`・`npm run build`成功）。
  - spec.md §4.4.1にも反映済み。

### ✅ 3-4. 「広告接続／期間選択／施策一覧／制作費用／施策マスタ管理」の5セクションが1ページに同居（2026-08-27ユーザー指摘・実装済み）

- **現状（旧）**：頻度も性質も異なる作業（広告接続・施策の有効/無効切替・クライアント固有施策追加、といった低頻度の設定操作と、日常の数値入力）が同一ページに詰め込まれ、§3-3の有効/無効管理パネルを追加した結果、日常入力の操作性がさらに悪化した（ユーザー指摘）。
- **実装済み（2026-08-27、4セッション目）**：低頻度の設定操作（広告アカウント接続状況・施策の有効/無効管理・クライアント固有施策マスタ管理）を`/agency/clients/[id]/campaigns/channels`（施策マスタ）として独立ページに分離した。`/agency/clients/[id]/campaigns`（日常の施策データ入力ページ）には`PageHeader`の右肩に「施策マスタ管理 →」リンクのみを残し、新ページ側には「← 施策データ入力に戻る」の戻りリンクを設置。

## 4. 目標設定（`/agency/clients/[id]/targets`）

### 🔴 4-1. 月ごとに1画面しか見えず、年単位の配分を見ながら入力できない（2026-08-27ユーザー確認済み・方針決定）

- **現状**：対象月を選ぶとその月のKPI一覧のみ表示。「先月はいくつに設定したか」「年間目標をどう配分したか」を別タブで確認しながら入力する必要がある。
- **背景**：住宅業界は展示会シーズン等で月ごとの繁閑差が大きく、目標も年間計画から月次に配分する形で決めることが多い。単月ごとの入力では年間の配分バランスを検算しづらい。
- **決定した方向性**：「KPI（縦）× 月（横12ヶ月）」のグリッドで年間分を1画面で一括入力・編集できるようにする。各行に年間合計を自動計算して表示し、配分の検算に使える。
  - **年度の区切り**：クライアントごとに事業年度の開始月を選択できるようにする（住宅会社は4月開始の会計年度が多いが、固定にはしない）。
    - `clients` テーブルに `fiscal_year_start_month`（int、1〜12、デフォルト4）のようなカラムを追加し、クライアント登録・編集画面で設定できるようにする。
    - グリッドの12列は、この開始月を起点に「開始月〜翌年開始月-1」の範囲で表示する（例：開始月=4なら2026年4月〜2027年3月）。
  - **データモデルへの影響**：会社全体KPI（来場予約数・来場数・契約数）については`targets`テーブル（KPI×月のUNIQUE制約）は変更不要で、このグリッドは既存の月次upsertをまとめて画面上で行うUI層の変更で済む。反響数目標については§9-1・§9-2の検討により`campaign_targets`（新テーブル）に置き換わった（**2026-08-27DB設計確定、`supabase/migrations/0004_channel_targets_budget_and_settings.sql`**）。
  - 「空欄保存＝未設定に戻す」という既存仕様（§4-3参照）は、年間グリッドでも同様に適用されるため、誤操作防止（確認ダイアログ等）とあわせて実装する。
- 併せて、各KPI行に前月・前年同月実績を薄く併記できるとより実務的（§4-2参照）。
- **【2026-08-27追記】このグリッドの「反響数」行は、その後§9-1・§9-2の検討で会社全体の単一値ではなくチャネル別の目標に置き換えることが決定した。** 本セクションの年間グリッドという表示形式自体はそのまま踏襲するが、KPI一覧に残るのは来場予約数・来場数・契約数の3項目＋チャネル別目標の自動集計値（合計反響数、読み取り専用）になる。詳細は§9-1・§9-2を参照。

### 🟡 4-2. 目標入力時に実績値の参考情報が一切ない

- 前月・前年同月の実績が分からないまま、根拠の薄い目標値を入力しがちになる。
- 改善案：各KPI行に前月・前年同月実績を薄く併記する。

### 🟡 4-3. 「空欄保存＝目標削除」という重要な仕様が注記テキストのみで、誤操作への防御がない

- 既存の目標値を誤って消してしまっても、確認ダイアログ等の防御がない。
- 改善案：値ありの欄が空欄化された状態での保存時のみ確認ダイアログを出す、または「クリア」操作を明示的なボタンとして分離する。

## 5. レポート（`/agency/clients/[id]/reports`, `/client/reports`）

### 🔴 5-1. spec上「PDFダウンロード」だが、実装は「ブラウザ印刷（`PrintButton`）」のみ

- 改善案：削除機能を追加する（確認ダイアログ必須）。

- spec.md §3には用語定義があるが、アプリのUI上（ファネル図やフォームラベル）にはツールチップ等の補足がない。特に新任の住宅会社担当者が迷う可能性がある。

## 9. アプリ全体のスコープ確認：不足している可能性のある機能（2026-08-27追加検討）

既存機能の使い勝手改善（§1〜6）とは別軸で、「KPI管理はあるのに対応する機能が丸ごと無い」という**機能スコープ自体の抜け**をユーザー指摘を受けて確認した。

### ✅ 9-1. 予算（費用計画）と実行費用の予実管理が存在しない（2026-08-27ユーザー提案・方針決定・モック確認済み・DB設計確定）

- **現状の欠落**：`targets`はleads_total／visit_reservations／visits／contractsという「成果指標」の目標のみを扱う。`campaign_metrics.cost`・`production_costs.amount`は「実際に使った費用」を記録するだけで、「いくら使う予定だったか（予算）」という計画値がアプリのどこにも存在しない。広告運用を管理するツールとして、「月間予算80万円のうち今50万円消化」のような基本的な予実表示ができない状態。
- **粒度（2026-08-27ユーザー確認済み）**：会社全体・拠点・チャネル別のすべてで予算を設定できるようにする。入力の手間は増えるが、年度はじめ・施策開始時にまとめて計画する性質の入力のため許容する、という前提。
- **確定したデータ設計（2026-08-27、`supabase/migrations/0004_channel_targets_budget_and_settings.sql`で実装）**：
  - 反響数目標（§9-2）と予算は同じ画面で常に一緒に編集されるため、別テーブルにはせず**単一テーブル`campaign_targets`**（`client_id` / `location_id` nullable / `channel_id` / `period_start` + `target_leads` + `budget_amount`）にまとめた。`campaign_metrics`（実績）と対になる「計画」テーブルという位置づけ。既存の「拠点別＋全社共通の合算＝会社全体」という集計ルール（spec §3・§6）・部分ユニークインデックスのパターンをそのまま流用する。
  - **「会社全体」の予算・反響数目標は、拠点別・チャネル別に入力された値の自動合算（ロールアップ）として算出する**（`targets`のような独立した1つの数値としては持たない）。理由：独立入力にすると「会社全体の値」と「内訳の合計」がズレたまま気づかれないリスクがある（ダブルメンテナンス）。この方式はモックで「合計反響数」を同じロールアップ方式（チャネル別目標の自動集計・読み取り専用）で実装し、ユーザー確認済み。
  - 対象は費用(cost)を持つ「広告」施策のみ（運用／オーガニック施策には費用の概念が無いため、DB制約ではなくアプリ層で絞り込む）。
  - 会社全体のKPI目標（来場予約数・来場数・契約数）は引き続き既存の`targets`テーブルに保存するが、`kpi_key='leads_total'`は廃止した（既存行は移行時に削除、campaign_targetsのロールアップに一本化）。
  - `clients.fiscal_year_start_month`（int、1〜12、デフォルト4）を追加し、年間グリッドの起点月をクライアントごとに設定できるようにした（§4-1）。
- **入力画面（2026-08-27方針決定・モックで確認済み）**：
  - 当初「KPI目標」と「予算」で入力画面を分ける方向を検討していたが、**チャネル別のリード目標（§9-2）を導入した結果、両者は同じ軸（チャネル×拠点×月）を持つことになったため、1つの画面の中で明確に連動させる形に変更した**（詳細は§9-2）。
  - タブ構成は次の2つ：

### ✅ 9-2. spec原文にあった「チャネル別の反響数目標」を実装する方針に確定（2026-08-27決定・9-1に統合）

- spec §4.4は目標の例として「合計反響数、**チャネル別反響数**、来場予約数、来場数、契約数など」を挙げていたが、Phase 8実装では`KPI_LABELS`（`src/lib/targets/kpiLabels.ts`）を4種（会社全体のみ）に絞り込み、チャネル別の反響数目標は実装されていなかった。
- **2026-08-27、ユーザーの指示により「チャネル別の反響数目標を導入し、予算と連動させて単価（想定CPL）を自動算出する」方針に確定**。単なる「実装を追加する」だけでなく、§9-1の予算機能と統合し、チャネルごとに「目標件数・予算・単価」を1セットで管理する設計にした（上記§9-1参照）。
- これにより、「このチャネルに予算を割いた分、反響が見合っているか（想定CPL通りに進んでいるか）」を計画段階から見られるようになる。会社全体の「合計反響数」は、このチャネル別目標の自動集計（読み取り専用）に置き換わる（§4-1にも追記済み）。

### 🟢 9-3. 「契約1件あたりの費用（CPA）」がどこにも表示されていない

- 契約金額・原価・粗利などの経営指標はspecで明確に「v1では扱わない」と決定されている（§9後回し）ため経営指標には踏み込まないが、契約1件を獲得するのにかかった費用（総費用÷契約数）は既存データ（費用・契約数）だけで算出でき、新たに売上や粗利のデータを必要としない。ファネル全体の効率を見る指標として、ダッシュボードの予実対比やチャネル別内訳に追加すると効果的。
- 優先度は低（無くても致命的ではないが、§9-1の予算予実と並べると特に有用）。

### ✅ 9-4. クライアントに外部アプリ連携用の識別子が無い（2026-08-27ユーザー提案・実装済み）

  - `clients.external_client_id`（text、nullable、UNIQUE制約）を追加。**代理店が自由に入力・編集できるID**とする（自動生成コードではなく、任意の文字列）。未設定のクライアントが複数あっても問題ない（UNIQUE制約はnullを複数許容）。
